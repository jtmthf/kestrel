# Subscription authentication for ACP runtimes

Research checked 16 September 2026 against official vendor documentation and the maintained ACP adapter repositories. This is a feasibility note, not a completed authenticated run.

## Codex: feasible on a trusted private host

The maintained [`@agentclientprotocol/codex-acp` adapter](https://github.com/agentclientprotocol/codex-acp#authentication) wraps the Codex App Server and supports ChatGPT login. The older `zed-industries/codex-acp` repository is [archived and directs new installs to this adapter](https://github.com/zed-industries/codex-acp#readme). For a headless environment, OpenAI documents `codex login --device-auth` (after device login is enabled on the account), or copying a file-backed `auth.json` from a trusted browser-equipped machine. The App Server also exposes a device-code login method. See [OpenAI authentication](https://learn.chatgpt.com/docs/auth) and [App Server authentication](https://learn.chatgpt.com/docs/app-server#authentication).

Set `cli_auth_credentials_store = "file"` and give Codex a persistent `CODEX_HOME` outside ephemeral task containers. Codex refreshes ChatGPT tokens during normal use and writes the refreshed `auth.json` back. OpenAI's [CI guidance](https://learn.chatgpt.com/docs/auth/ci-cd-auth) requires that updated file to survive later runs and recommends a single machine or serialized stream per credential copy; concurrent isolated copies can race token rotation. The file contains bearer credentials and must stay outside the repository, logs, and artifacts. OpenAI recommends API keys for general automation, but specifically documents this account-auth pattern for trusted private automation that requires the user's Codex account.

An ACP smoke test can verify `initialize`, `session/new`, and a harmless prompt using a host-managed credential mount. It should report only auth mode and success/failure, never token contents. A second run after process restart verifies persistence. A later refresh check must observe the credential file through a secret-safe diagnostic and verify the changed file survives into another run; a one-off successful login cannot prove refresh behavior. [OpenAI CI guidance](https://learn.chatgpt.com/docs/auth/ci-cd-auth) supports these checks.

## Claude: technical path exists; third-party entitlement is unresolved

The maintained [`claude-agent-acp`](https://github.com/agentclientprotocol/claude-agent-acp#readme) implements ACP through the Claude Agent SDK. Claude Code can use a subscription login from `/login`; on Linux it stores credentials at `~/.claude/.credentials.json` (or under `CLAUDE_CONFIG_DIR`). It coordinates renewal across parallel sessions, but an expired login that cannot refresh requires another login. For unattended scripts, `claude setup-token` produces a one-year subscription OAuth token for `CLAUDE_CODE_OAUTH_TOKEN`; the command does not persist the token, and `--bare` does not read it. See [Claude authentication](https://code.claude.com/docs/en/team) and [login troubleshooting](https://code.claude.com/docs/en/troubleshoot-install). These are potential container provisioning paths; the SDK adapter's behavior with either path still needs an authenticated smoke test.

There is a material documentation conflict. Anthropic's [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) says third-party developers may not offer claude.ai login or subscription rate limits through SDK-based products without prior approval. Anthropic's [June 2026 subscription help article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) says a proposed change was paused and that third-party app use currently continues to draw from subscription limits. Since the ACP adapter uses the SDK, these pages do not establish that Kestrel may ship a Claude subscription path as a third-party product. A successful local call would establish technical operation, not resolve that policy conflict. Seek authoritative clarification before treating Claude subscription through this adapter as a supported product dependency.

For a technical smoke test, a user can provision the credential through a private secret path; Kestrel need only receive the resulting mount or environment variable. Run a minimal `initialize`, `session/new`, and prompt inside the target Linux image, then repeat in a fresh container. Check authentication status and record only nonsecret outcomes. No user credential should be pasted into a ticket, research note, command log, or test fixture. [Claude authentication](https://code.claude.com/docs/en/team) documents the supported credential mechanisms.

## OpenCode: subscription access can still require a key

The [provider documentation at the pinned v1.18.29 tag](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/web/src/content/docs/providers.mdx) documents no-key OAuth paths for ChatGPT Plus/Pro, GitHub Copilot, experimental GitLab Duo, and qualifying SuperGrok/X Premium plans. OpenCode Go is a subscription but requires an OpenCode-issued API key; OpenCode Zen also requires a key. This distinguishes a subscription product credential from a separately provisioned model-provider API account. The same versioned documentation warns that Claude Pro/Max through third-party OpenCode plugins is prohibited and not bundled; do not treat it as the Claude Code ACP path.

OpenCode ACP uses existing provider authentication; the human must first complete `opencode auth login` in a terminal. Its [ACP documentation](https://opencode.ai/docs/acp/) does not present ACP authentication as the login UI. In the [pinned ACP source](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/acp/service.ts), the advertised `opencode-login` authentication method is a no-op; Kestrel can use `--agent-auth opencode-login` to satisfy its method check, but this does not create credentials. The [pinned auth store](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/auth/index.ts) writes OAuth access and refresh tokens to `~/.local/share/opencode/auth.json` with mode `0600`.

For local dogfooding, a private persistent auth volume can carry that file into fresh task containers without baking it into the image or repository. This is not isolation from the agent: the OpenCode process and its shell tools run as the same user and can read the credential file. A real model-call smoke therefore needs the user's OpenCode Go key already configured in that volume, or a fresh interactive `opencode auth login` first. Check only success/failure and the presence of usable login, never credential contents.

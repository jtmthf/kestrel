# Portable issue readiness for Kestrel

Research gathered 2026-09-16 from first-party documentation. The design proposal below is an inference from the tracker APIs, not a behavior promised by those APIs.

## Tracker facts

| Tracker | Delegation signal | Blockers and current state | Change signals |
| --- | --- | --- | --- |
| GitHub | An `issues` webhook has an `assigned` action and an `assignee`; the issue API supplies current assignees and state. [Webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [issue API](https://docs.github.com/en/rest/issues/issues#get-an-issue) | Native issue dependencies can be listed with `GET /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by`. Each blocking issue can be checked for open/closed state. Pagination is required. [Issue dependencies API](https://docs.github.com/en/rest/issues/issue-dependencies) | `issues` actions cover assignment and issue state; `issue_dependencies` has a documented `blocked_by_added` action. Do not rely on a dependency-removal action without verifying it: the current webhook reference only documents `blocked_by_added`. [Webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads) |
| Linear | Assigning an issue to an app user sets `Issue.delegate`, while a human remains `Issue.assignee`. Mentioning or delegating to the app creates an `AgentSessionEvent`. The Agent APIs are still in developer preview. [Agents API](https://linear.app/developers/agents) | Linear has explicit *Blocked by* and *Blocks* relations. When the blocker is resolved, the relation moves under *Related* in the UI. The GraphQL API supports querying an issue, and schema introspection is available to establish the precise relation fields before implementation. [Issue relations](https://linear.app/docs/issue-relations), [GraphQL API](https://linear.app/developers/graphql) | Data-change webhooks support Issue, Comment, and IssueLabel entities, with create/update/remove actions and `updatedFrom` on updates. Agent session webhooks cover delegation and mentions. The public webhook guide does not list a dedicated issue-relation event; use Issue updates as hints and reconcile. [Webhooks](https://linear.app/developers/webhooks), [Agents API](https://linear.app/developers/agents) |
| Jira Cloud | The issue API exposes the current `assignee`; assignment uses an account ID. There is no first-party agent-delegate concept in the cited issue API. [Issue API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) | Issue links are exposed by `GET /rest/api/3/issue/{issueIdOrKey}`; link type names and `inward`/`outward` descriptions are administrator configurable. A `Blocks` link typically uses `is blocked by` inward and `blocks` outward, so an adapter must identify the configured link type and direction, then inspect each linked issue's current status. [Issue linking model](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/), [issue API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) | Jira Cloud has `jira:issue_updated`, `issuelink_created`, and `issuelink_deleted` webhooks. Delivery can be retried, and some bulk/cascade webhooks are delayed. [Webhooks](https://developer.atlassian.com/cloud/jira/software/webhooks/) |

## Design inference

A trigger should match a **request to consider work**: assignment/delegation, an authorized mention, or an explicit dispatch. A separate tracker adapter should fetch a **fresh readiness snapshot** before Kestrel opens a session. Normalize the snapshot to `work item identity`, `open/terminal state`, `delegated to Kestrel?`, and `unresolved blockers`, while retaining tracker-specific evidence and IDs. The base automatic policy is: delegation still exists, the item remains open, and there are no unresolved blockers. An explicit dispatch can carry a recorded blocker override. The event alone is insufficient because a blocker can change after the original assignment, and Jira/Linear encode blockers differently. [GitHub dependencies](https://docs.github.com/en/rest/issues/issue-dependencies), [Linear agents](https://linear.app/developers/agents), [Jira issue linking](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)

Persist a held request and its reason, then reevaluate when a relevant webhook arrives **and** through periodic reconciliation. Recheck immediately before claiming work; if the tracker cannot be queried, keep the request held with an unknown-readiness reason. Reconciliation matters because webhook streams are not a durable source of current truth: Linear retries failed deliveries only a limited number of times, Jira can retry and delay them, and GitHub's published dependency webhook actions do not presently document removal. [Linear webhooks](https://linear.app/developers/webhooks), [Jira webhooks](https://developer.atlassian.com/cloud/jira/software/webhooks/), [GitHub webhooks](https://docs.github.com/en/webhooks/webhook-events-and-payloads)

The portability boundary is the adapter's readiness snapshot, not a cross-tracker expression inside event filter syntax. Trigger filters can still express source-specific intent, such as a GitHub `issues.assigned` event, but a live blocker test is a query over other work items. Linear also shows why the normalized concept should be **delegated to Kestrel**, rather than **assignee equals Kestrel**. [GitHub webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [Linear agents](https://linear.app/developers/agents), [Jira issue linking](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)

## Implementation questions to resolve later

- Confirm Linear's exact GraphQL fields for active blocking relations by introspecting the version of its schema available to the integration; the public guides establish the concept, but do not pin those fields. [GraphQL API](https://linear.app/developers/graphql), [Issue relations](https://linear.app/docs/issue-relations)
- Configure Jira's blocking link type by ID or verified inward/outward labels per site; do not assume every Jira site names it `Blocks`. [Issue linking model](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)
- Decide each tracker's terminal-state mapping, especially Jira workflows with custom statuses; a single `closed` string is not portable. [Jira issue API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/), [Linear issue relations](https://linear.app/docs/issue-relations)

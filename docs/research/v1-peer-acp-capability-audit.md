# Peer and ACP capability evidence for an expansive v1

Research for [Research peer and ACP capability gaps for v1](https://github.com/jtmthf/kestrel/issues/190), 2026-09-16. This note identifies decision candidates; it does not choose Kestrel's v1 floor. Product claims below come from first-party documentation, and Kestrel claims from this repository's current source and decisions.

## The named gaps

| Candidate | Peer evidence | Kestrel coverage and decision seam |
| --- | --- | --- |
| Human web UI | [Cursor's web and mobile agent](https://docs.cursor.com/en/background-agent/web-and-mobile) starts work, shows it, supports feedback on diffs and PR management; its [team dashboard](https://docs.cursor.com/en/account/teams/dashboard) shows agent status, logs, resource use, integrations and usage. [OpenHands](https://docs.openhands.dev/openhands/usage/cli/quick-start) offers a full web GUI alongside its CLI. | [README](../../README.md#what-v1-means) names multiplayer and governance, and [ROADMAP](../../ROADMAP.md#03--kestrels-work-is-joinable-mid-flight) promises an interactive Client, but neither explicitly places a human web UI. [ADR-0001](../adr/0001-rust-control-plane-typescript-supervisor.md) already refers to a `0.3` TypeScript web UI. Decide whether a browser Client is required, its first rung, and the minimum session, approval and operator views. This is a placement/acceptance gap, not evidence that a new domain concept is needed. |
| Skills and reusable instructions | [GitHub Copilot](https://docs.github.com/en/copilot/reference/customization-cheat-sheet) documents skills, custom instructions, agents, hooks and MCP as separate customization mechanisms; [OpenHands](https://docs.openhands.dev/openhands/usage/customization/repository) supports repository skills and setup scripts; [Devin](https://docs.devin.ai/product-guides/creating-playbooks) has reusable, shareable playbooks. | [Kestrel's Agent](../../CONTEXT.md#actors) owns instructions, and a [Brief](../../CONTEXT.md#cause) starts a Session, but [README](../../README.md#what-v1-means) and [ROADMAP](../../ROADMAP.md) promise no discovery, installation, versioning or invocation contract for reusable skills. Decide whether Kestrel only passes runtime-native skill directories, or owns an organization/workspace skill catalog and how a Run pins what it used. ACP itself has no standard skill-install method; use runtime files or tool configuration rather than assuming one. |
| MCP tools and external context | [GitHub Copilot custom agents](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-custom-agents) can declare MCP servers; [OpenHands CLI](https://docs.openhands.dev/openhands/usage/cli/command-reference) manages HTTP, SSE and stdio servers. [ACP v1 session setup](https://agentclientprotocol.com/protocol/v1/session-setup) accepts `mcpServers` for `session/new`, `session/load` and `session/resume`; HTTP and SSE support are advertised capabilities, not universal. | [ADR-0007](../adr/0007-acp-is-the-agent-runtime-contract.md) explicitly selects an MCP server for Kestrel-owned tool operations, and [pending-event issue](https://github.com/jtmthf/kestrel/issues/90) already specifies one use. [Supervisor source](../../crates/kestrel-supervisor/src/runtime.rs) currently sends `NewSessionRequest::new(working_directory())` without a server list. Decide the operator-facing MCP server declaration, credential scope, transport support, tool policy and how Kestrel injects its own server. Keep generic MCP configuration distinct from the pending-event tool. |

## ACP constraints that affect the decisions

1. ACP is Kestrel's **Agent Runtime** boundary, not its human Client API ([ADR-0007](../adr/0007-acp-is-the-agent-runtime-contract.md), [ACP architecture](https://agentclientprotocol.com/get-started/architecture)). Kestrel can build UI and skill management around it, but cannot promise that every runtime accepts a skill or exposes every capability.
2. A Client supplies MCP servers when creating/loading/resuming an ACP conversation. Stdio is the baseline; HTTP and SSE require runtime capability advertisement ([ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). Kestrel needs to decide how declarations and secrets become those per-Run parameters. The current [supervisor call](../../crates/kestrel-supervisor/src/runtime.rs) passes only the working directory.
3. ACP capabilities are optional and omitted ones are unsupported ([ACP initialization](https://agentclientprotocol.com/protocol/v1/initialization)). Model/configuration, resume and richer tool surfaces therefore need a capability-aware UX. The [v2 specification](https://agentclientprotocol.com/protocol/v2/overview) is published as draft; the existing [ADR-0007](../adr/0007-acp-is-the-agent-runtime-contract.md) says to speak v1 while shaping for v2.
4. ACP `session/load` replays runtime history, while `session/resume` restores context without replay, and both are capability gated ([ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). Kestrel's durable transcript and its runtime conversation are separate objects. Any continuity promise must state which one survived.

## Precise questions now ready for product decisions

1. Which browser Client capabilities are required at v1: start and follow a Session, read transcript/diff/files, answer an Approval or Question, inspect queue/Campaign/Trigger state, and administer the Organization? Which rung first owns that Client?
2. What is a Kestrel-managed skill, if any: a pass-through runtime directory, a versioned Workspace or Organization asset, or just Agent instructions? What gets pinned in a Run's audit record?
3. Which MCP servers may be declared at Organization, Workspace, Agent and Run scope; how are credentials delivered; and how do policy and audit bind a tool invocation? Which transports must the two-runtime v1 gate demonstrate?
4. What operator visibility constitutes completion of the nine existing promises: trigger test and firing trace; queue and spend; Instance access; effective model; continuity status; Campaign graph; participant access; audit search/export?

These questions are narrower than “parity” because each names a user-visible acceptance boundary. The decision maker can require, defer or declare existing coverage for each without treating any peer's implementation as Kestrel's design.
